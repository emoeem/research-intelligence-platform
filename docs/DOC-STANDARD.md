# 文档规范（RIP research-platform）

> 本文件是 research-platform `docs/` 的写作与维护标准，对齐 telegram-bot 项目 `docs/DOC-STANDARD.md`（2026-11-09 版）的框架，按 RIP 实际技术栈改写字段。所有新写、改写的文档都要满足这里的硬性要求；规范本身随实践演进，改动需在提交信息里写明理由。适用对象：维护者与接手的 AI 助手。

| 项       | 值                                        |
| -------- | ----------------------------------------- |
| 状态     | 生效中                                    |
| 日期     | 2026-11-09（首次制定）                    |
| 适用版本 | git `352b3df` 及之后                      |
| 相关     | docs/SESSION-HANDOFF.md、docs/phase0/PHASE-ROADMAP.md |

## 一、三条底线

1. **数字必须实测，写明来源。** 测试数来自 `cargo test` 与 `python3 -m unittest` 的实际输出，迁移号来自 `migrations/` 目录，提交哈希来自 `git log`。禁止写「大约」「可能有几十个」；拿不到数就写「未测」，不要编。
2. **讲「为什么」，不只讲「是什么」。** 每条结论都要能回答：当时为什么这样做？不这样做会出什么事？纯清单式 changelog 不合格。
3. **坏消息必须写。** 未做项、已知限制、失败过的尝试、需要人工补的步骤，一律单列章节。只写好话的文档视为不完整。

## 二、放哪、叫什么

| 类型     | 目录          | 命名                                              | 例子                                   |
| -------- | ------------- | ------------------------------------------------- | -------------------------------------- |
| 更新记录 | `docs/releases/` | `RELEASE_YYYY-MM-DD_主题.md`，同日多批加主题后缀 | `RELEASE_2026-11-09_PHASE1.md`         |
| 阶段设计 | `docs/phaseN/`   | 大写下划线主题文件                               | `docs/phase2/PHASE2-DESIGN.md`         |
| 审计     | `docs/audits/`   | `*_AUDIT_YYYY-MM-DD.md`                          | 待建                                   |
| 手册     | `docs/guides/`   | 大写下划线                                       | 待建                                   |
| 运维     | `docs/ops/`      | 小写连字符或大写下划线                           | 待建                                   |
| 交接     | `docs/` 根    | `SESSION-HANDOFF.md`                             | 唯一跨会话状态源                       |
| 路线图   | `docs/phase0/`   | `PHASE-ROADMAP.md`                               | Phase 1 到 10 依赖冻结                 |

规则：

- 日期一律 `YYYY-MM-DD`；文件名只允许字母、数字、`_`、`-`、`.`，不用中文文件名。
- 同一主题系列文档保持同目录，用日期或主题后缀区分，不用 `_PART2`。
- 全文禁止 em dash 与 en dash（长横线），用逗号、冒号、括号替代。

## 三、与 RIP 项目隔离的硬规则（文档不得影响工程）

1. 文档只存在于 `docs/`；任何代码、schema、迁移、CI 配置不得引用文档路径，文档路径变化不需要改代码。
2. 三道门禁（`cargo test`、`cargo clippy`、`python3 -m unittest`）不扫描 markdown；写文档不构成门禁通过的理由，门禁失败不得以「文档说明了」豁免。
3. 更新记录是快照：只记当时实测事实，事后状态变化写在新的 RELEASE 里，不回头改旧 RELEASE。
4. 不写密钥、Token、密码、连接串；写「见本地密钥管理」即可。生产数据库内容不进文档。
5. 文档写入时机在验收之后（入库批次内），不先写结论后补事实。

## 四、更新记录（releases/）必备内容

读者是维护者与接手的 AI。必备：

1. **引语**（blockquote）：2 到 5 行，说清本阶段用户能感知到什么、修掉了什么隐患。
2. **元信息表**（字段固定）：`阶段交付`（git 短哈希 + 时间 CST）、`数据库迁移`（迁移号 + 在哪个副本验证 + 生产库是否触及）、`自动化测试`（cargo test 与 unittest 实测数，与上阶段对比）、`静态检查`（clippy 结果）。
3. **分章正文**：每章一个主题。新能力写默认值选择理由；修复写根因。
4. **已知取舍**：做不到的、留待下阶段的、有风险的。
5. 涉及回滚的改动给出回滚方式（git revert 目标哈希或迁移回退说明）。

## 五、通用骨架

- 开头 10 行内交代：状态、日期、适用版本、相关文档（表格）。
- 只有一个 H1；章节用 `## 一、二、三`。
- 每节先结论后细节；表格只放可枚举事实，解释写正文。
- 代码块标语言，命令可直接复制执行。
- 引用代码位置写 `crates/foo/src/bar.rs:123` 形式。

## 六、提交前检查清单

```bash
grep -rP '\x{2014}|\x{2013}' docs/ ; echo "exit=$?（1 为零命中，通过）"
```

- [ ] 标题说清「这是什么」
- [ ] 头部有状态与日期
- [ ] 所有数字有来源，无估算值
- [ ] 未做项与已知限制已单列
- [ ] 无密钥与生产数据
- [ ] em/en dash 零命中
- [ ] 新文档已登记进 docs/README.md

链接检查暂无自动化脚本（不为此在宿主机装工具）；跨文件引用写仓库根相对路径并人工核对。

## 七、模板

### 7.1 更新记录

```markdown
# 更新说明 · <YYYY-MM-DD>（<主题>）

> <2 到 5 行引语。>

| 项         | 值                                                  |
| ---------- | --------------------------------------------------- |
| 阶段交付   | git `<短哈希>`（<HH:MM> CST）                       |
| 数据库迁移 | <无新增 / 00XX_name.sql 在 dev 副本验证；生产库未动> |
| 自动化测试 | cargo test `<N>` 全绿；unittest `<M>` 全绿（跳过 `<k>`） |
| 静态检查   | cargo clippy `-D warnings` 零告警                   |

## 一、<面向使用者的变化>

## 二、<修复与根因>

## 三、已知取舍
```

### 7.2 审计

```markdown
# <范围>审计 · <YYYY-MM-DD>

> 快照性质：结论反映审计当日代码状态。

## 范围与方法
## 结论（严重程度 | 位置 | 问题 | 建议）
## 已核实无问题
## 汇总
```

## 八、维护这份规范

- 新增文档类型时先在本文档补一节再写第一份实例。
- 修改规范时提交信息写清「为什么改」与「既有文档是否已回补」。
