## 0. 给接手 AI 的最高优先级指令

你接手的是一个已经完成 RIP 2.0 多阶段建设、具有真实 Rust Core、Python Workers、REST/MCP/CLI 和 React Web 工作台的项目。Figma 中也已经建立了一套基础视觉方向。

**本任务不是重新设计或重写整个 RIP，也不是一次性把所有业务页面画完。**

你必须遵守以下原则：

1. **先理解现状，再动手。** 先读取仓库的 `AGENTS.md`、`README.md`、`docs/SESSION-HANDOFF.md`、`docs/README.md`，再检查 `web/` 的实际代码、路由、组件、样式和测试。
2. **Figma 是视觉基准，不是业务事实来源。** Figma 用来约束布局、视觉、组件和交互意图；实际业务能力、API、状态、数据结构必须以仓库代码、Schema 和契约文档为准。
3. **保留现有架构和功能。** 不得因为设计稿或个人偏好重写 Rust Core、Python Workers、服务端、API、数据库或整个 Web 前端。
4. **先复用，再扩展。** 优先复用现有组件、依赖、设计 Token、API 和状态管理。只有确认现有能力无法满足需求，才增加新实现。
5. **一次只做一个明确批次。** 每批先审计、列最小计划、实施、测试、视觉验收、更新文档；不得未经要求一次性铺开所有页面。
6. **真实数据优先。** 不得把静态数字、假日志、假运行状态伪装成生产数据。Mock 必须明确隔离并标注。
7. **设计持续演进。** 新增功能时优先在现有 Figma 文件和组件体系中补充，不创建平行设计系统，不随意推翻已有视觉方向。

如果本文件与仓库当前实际实现冲突，以实际代码、当前有效契约及仓库级 `AGENTS.md` 为准；先记录差异，再提出最小修订，不得自行猜测。

## 1. 产品定位与设计目标

RIP 是面向安全研究、情报治理和 AI 辅助研究的专业工作平台。它不是普通 CRUD 管理后台，也不是只提供聊天窗口的 AI 产品。

平台现有能力覆盖：

- 资源入库、来源与元数据管理；
- 统一资源检索与 Resolver；
- 知识库、质量治理与审核；
- 研究任务、证据与发现；
- 安全工具注册、契约和隔离执行；
- Agent 定义、运行与审计；
- Workflow 定义、编排、运行控制；
- REST、MCP、CLI 等对外接口；
- 报告、运行记录、Trace 和系统状态。

UI 的核心任务是把这些能力组织成清晰、可追踪、可操作的工作台，让用户能够回答：

- 当前系统有什么数据、资源和能力？
- 某项研究进行到哪一步，依据是什么？
- 某个资源来自哪里，质量如何，是否可信？
- 某个工具或 Agent 能做什么，权限边界是什么？
- 一次运行做了什么、何时完成、失败在哪里？
- 一个结论能否追溯到来源、证据和执行链？

设计目标按优先级排序：

1. 信息准确、来源可追溯；
2. 导航清晰、任务路径明确；
3. 高密度信息仍然易读；
4. 操作状态明确、反馈及时；
5. 安全边界可见且不易误操作；
6. 组件复用和后续扩展成本低；
7. 视觉精致，但不以装饰牺牲可用性。

## 3. 视觉语言与设计 Token

整体定位：专业、克制、信息密集的安全研究工作台。

关键词：石墨深色界面、低饱和蓝紫强调色、清晰层次、细边框、紧凑但舒适的数据布局。

### 3.1 当前基础色板

以下为当前 Figma 基础方案的起始 Token。实施时先检查 `web/` 是否已有等价 CSS Variables / Tailwind Theme / daisyUI Theme；如已有，应映射到现有命名，不要创建重复 Token。

| Token 建议名 | 色值 | 用途 |
|---|---|---|
| `--rip-bg` | `#111318` | 页面主背景 |
| `--rip-sidebar` | `#151820` | 全局侧边栏 |
| `--rip-surface` | `#191D25` | 卡片、面板 |
| `--rip-surface-raised` | `#202530` | 输入框、浮层、次级容器 |
| `--rip-border` | `#2B313D` | 分隔线、描边 |
| `--rip-text` | `#EEF1F7` | 主文字 |
| `--rip-muted` | `#929BAD` | 次级文字 |
| `--rip-accent` | `#A895FF` | 主强调色 |
| `--rip-accent-strong` | `#7564D8` | 强调色深阶 |
| `--rip-success` | `#52C79A` | 成功、健康、已验证 |
| `--rip-warning` | `#E9B96E` | 待审核、警告 |
| `--rip-danger` | `#E87983` | 错误、危险、拒绝 |
| `--rip-info` | `#75A9F4` | 信息、辅助提示 |

状态色不能只靠颜色表达，必须同时配合文字、图标或状态说明。

### 3.2 字体和排版

- 当前 Figma 基础方案使用 Inter 作为拉丁字符基准。
- 中文字体必须使用合理的系统回退栈；不得假设所有部署环境都安装同一字体。
- 页面标题、区块标题、正文、表格元数据应建立明确层级。
- 不要把所有文字都做成小号灰字；关键数据、操作结果和错误说明必须有足够对比度。
- 代码、JSON、日志、ID、Trace ID 等适合使用等宽字体。
- 需要检查 Linux Chromium/Firefox 下的实际字体回退和字重渲染。

### 3.3 间距、圆角和密度

基础参考：

- 采用 4px 或 8px 递进的间距体系；
- 普通卡片圆角约 12px；
- 输入框和按钮圆角约 6–8px；
- 浮层和大型容器可使用 12–16px；
- 以边框、背景层级和留白区分区域，不依赖厚重阴影；
- 数据表格保持较高信息密度，但行高、列间距和文字对比度必须可读。

不要在单个页面私自发明新的间距、圆角或颜色值。确有必要时先更新设计规范。

### 3.4 明确禁止的视觉方向

- 大面积渐变、霓虹描边、过度发光；
- 纯黑背景和刺眼高饱和色；
- 为了“科技感”添加无意义的网格、粒子和装饰图；
- 每个卡片都使用不同颜色；
- 无实际信息价值的装饰性仪表盘；
- 过度圆润、玩具化的控件；
- 用大量空白和巨型标题浪费研究工作区空间；
- 用静态截图伪装成可交互功能。

## 4. 真实前端技术基线

根据仓库当前文档，Web 工作台位于 `web/`，采用 React 19、Vite、TypeScript。当前依赖清单还记录了：

- React Router：路由；
- TanStack Query：服务端数据请求、缓存和状态同步；
- Tailwind CSS 4 + daisyUI 5：样式与基础组件能力；
- Lucide React：图标；
- ECharts：图表；
- @xyflow/react：Workflow Studio 画布；
- Vitest + Testing Library：单元与组件测试；
- Playwright：浏览器 E2E 与视觉门禁；
- axe-core：无障碍检查。

**这是一份现有技术基线，不是要求无条件升级或重装依赖的清单。** AI 必须读取 `web/package.json`、锁文件和实际源码核对版本、依赖使用情况。新增依赖必须遵守仓库 `AGENTS.md` 的成熟库优先和依赖审计要求。

仓库当前架构还包括：

- `crates/`：Rust workspace 与核心领域/引擎；
- `workers/python/`：Python Workers；
- `apps/server/`：现有 Web 服务和 API 承载；
- `schemas/`：工具、插件、工作流、研究等契约；
- `migrations/`：数据库 Schema 与数据迁移；
- `integrations/rtis/`：RTIS 生产接入与知识栈；
- `web/`：React Web 工作台。

不得将本文档中“建议的页面组织”误解为要求改变现有服务端、API 或核心架构。

## 5. 全局应用布局基准

以现有 Overview 画板的整体结构为基础，逐步统一全站布局。

### 5.1 全局侧边栏

负责主模块导航。基础分组建议：

**Workspace**
- Overview
- Projects
- Research
- Knowledge Base

**Capabilities**
- Tool Center
- Agents
- Workflows

**Operations**
- Runs
- Runtime
- Reports

**System**
- Settings

注意：以上是导航信息架构建议。实施前必须对照当前路由和已交付工作区，保留现有可用入口；如果实际路由名称或分组不同，以现有功能为准，避免导航指向不存在的页面。

要求：

- 当前路由高亮；
- 支持合理的分组与折叠；
- 图标风格统一；
- 窄屏时能切换为抽屉或紧凑导航；
- 不允许每个页面复制一份不同的侧边栏；
- 未实现的入口不能伪装成可用功能。

### 5.2 顶部工具栏

基础元素：

- 面包屑或当前页面标题；
- 全局搜索入口；
- 当前系统健康状态；
- 用户/工作区入口；
- 与当前页面相关的主要操作（按页面需要出现）。

顶部栏不能塞入所有功能按钮。页面操作应放在页面标题区或对应内容区域。

### 5.3 内容工作区

- 使用统一的内容最大宽度和页面边距策略；
- 页面标题区包含标题、简短说明和主要操作；
- 卡片、表格、过滤器和详情面板遵循统一间距；
- 支持宽屏多列布局和较窄视口的自然重排；
- 复杂研究页面允许采用可调整的多面板布局，但不能破坏主导航。

## 7. 页面扩展策略

**当前只要求保留一套基础设计，并逐步扩展。以下内容是长期页面能力地图，不是要求本次一次性实现。**

### 7.1 Overview

目标：快速了解系统和研究工作全局。

后续按真实 API 能力逐步加入：

- 研究任务与项目概览；
- 资源入库、治理和质量概览；
- 工具、Agent、Workflow 运行摘要；
- 最近活动和待处理事项；
- Runtime 健康状态；
- 常用入口。

图表必须回答实际问题。没有真实数据源时展示明确的 unavailable/未配置状态，不得展示虚构 KPI。

### 7.2 Projects / Research

目标：管理研究上下文和研究过程。

可逐步完善：

- 项目列表与项目详情；
- 研究任务列表、筛选与优先级；
- 研究目标、范围和状态；
- 研究笔记、假设、发现；
- 证据、来源和关联资源；
- 任务执行历史与 Trace；
- 结果和报告关联。

### 7.3 Knowledge Base

目标：管理大量安全知识资源，并确保质量和来源可追溯。

可逐步完善：

- 资源列表、详情和分类；
- 来源、抓取时间、版本和许可证信息；
- 质量等级与治理状态；
- 审核/复核队列；
- 重复资源识别与合并流程；
- 资源与 Skill、工具、研究任务的关联；
- 检索结果解释和覆盖信息；
- 知识图谱（只有真实关系数据和明确用途时才加入）。

性能要求：

- 使用服务端分页、游标或现有 API 支持的分页方式；
- 使用后端过滤和排序，避免前端拉取整个资源库；
- 大型表格按需采用虚拟滚动；
- 搜索输入应防抖并处理取消/过期请求；
- 详情按需加载，不要首屏加载全部关联对象；
- 缓存策略必须尊重数据更新和失效规则；
- 空数据、数据不可用和查询失败是不同状态，不能混为一谈。

### 7.4 Tool Center

目标：清晰呈现工具能力、可信状态和执行边界。

可逐步完善：

- 工具目录和分类；
- 工具详情、版本、来源和契约；
- 安装/启用/禁用状态；
- 依赖和容器镜像信息；
- 权限、网络范围、文件访问范围；
- 健康检查和执行历史；
- MCP/CLI 等暴露方式。

工具“注册/配置”与“执行”必须分开。任何执行操作都必须走现有 Rust Tool Engine / 安全执行链路及后端授权，不允许前端直接执行 Shell 或绕过执行面。

### 7.5 Agents

目标：配置、观察和管理 Agent，而不是只显示一个聊天窗口。

可逐步完善：

- Agent 定义和详情；
- 模型、Prompt、上下文和预算配置；
- 工具权限与可用能力；
- 运行状态、输入输出摘要；
- 运行历史、日志和 Trace；
- 失败原因、取消和重试（以后端支持为准）。

敏感配置不得在 UI 中明文回显。模型密钥、Token 等应使用后端安全存储和脱敏显示。

### 7.6 Workflows

目标：可视化构建、验证和运行真实工作流。

当前仓库已有 Workflow Studio 与 `@xyflow/react` 依赖基线。扩展时优先复用现有画布和工作流契约。

可逐步完善：

- 工作流列表和版本；
- 节点、边和画布；
- 节点配置面板；
- 输入输出 Schema；
- 条件分支和错误路径；
- 静态校验结果；
- 人工审批节点；
- 运行预览、执行历史和失败定位。

画布节点不能只是一张静态示意图。保存、验证、运行、暂停、恢复、重试等行为必须遵循现有 Workflow API/CLI/Engine 契约。

### 7.7 Runs / Runtime

目标：可解释地观察执行过程和系统健康。

可逐步完善：

- 运行列表和过滤；
- Run 详情与节点状态；
- 日志、Artifact、Evidence；
- Trace / Correlation 关联；
- 失败原因与重试；
- Worker、队列、服务、数据库状态；
- 心跳和资源指标。

运行状态必须来自真实服务端。需要区分 queued、running、paused、succeeded、failed、cancelled 等实际状态；具体枚举以当前状态机契约为准。

### 7.8 Reports

目标：形成可审阅、可追溯的研究交付物。

可逐步完善：

- 报告列表和详情；
- 报告模板；
- 章节与内容编辑；
- 发现、证据和来源引用；
- 导出与版本；
- 审阅状态和审计记录。

报告中的结论必须保留证据引用，不得自动把未经验证的 Agent 输出标记为事实。

### 7.9 Settings / Audit

目标：提供系统级配置、权限与可审计性。

可逐步完善：

- 用户和角色；
- 系统配置；
- 模型与 API 配置；
- MCP 和插件配置；
- 安全策略；
- 审计事件和操作历史。

权限必须由服务端执行。前端隐藏按钮只是体验控制，绝不是安全边界。

## 8. 数据、API 与 UI 的边界

### 8.1 以现有 API 契约为准

当前 REST API 契约见：

- `docs/phase9/REST-API-CONTRACT.md`
- `docs/phase9/PHASE9-DESIGN.md`
- 对应服务实现：`apps/server/rp_server.py`

同时检查 MCP、CLI、Workflow、Agent 和 Tool 的现有契约。不要根据页面设计稿发明接口字段、状态枚举或写入路径。

### 8.2 数据请求规范

- 服务端数据请求优先复用现有 TanStack Query 模式（先核实当前代码）。
- API Client 应统一处理 Bearer Token、错误信封、超时和取消。
- 对 `available: false`、真实空列表、鉴权失败、服务不可用和网络错误分别展示。
- 列表页使用服务端分页/过滤，不要把数据库全量数据搬到浏览器。
- 对写操作进行输入校验、重复提交保护和结果反馈。
- 修改成功后按数据依赖正确刷新或更新缓存。
- 错误信息给用户可理解的解释，同时保留可供排查的错误码/Trace ID。

### 8.3 Mock 数据纪律

Mock 只允许用于 Storybook/组件演示、测试夹具或明确标注的开发预览。

- Mock 文件和真实 API Client 分离；
- 页面显著标明 Demo/Mock；
- 不得在生产构建中静默回退到假数据；
- 不得用固定成功响应掩盖后端错误；
- 不得用随机数字制造“实时运行”效果；
- API 未实现时展示未接入状态，并记录 API 缺口。

## 9. 安全、权限与高风险交互

RIP 面向安全研究，必须让用户清楚知道“将执行什么、由谁执行、在哪里执行、具有什么权限”。

所有高风险操作应在交互中体现：

- 操作对象和影响范围；
- 运行环境/容器；
- 网络访问范围；
- 文件系统挂载范围；
- 使用的工具和版本；
- 是否需要审批；
- 取消方式；
- 运行结果与审计记录。

安全要求：

1. 不得由前端直接执行任意 Shell 命令。
2. 不得绕过 Rust Tool Engine、容器隔离或现有权限检查。
3. 不得把前端按钮是否可见当成授权判断。
4. 高风险操作应有明确确认和服务端审批状态。
5. Secret、Token、Cookie、密钥不得写入日志或前端持久化存储。
6. 错误提示不得泄露堆栈、内部路径、密钥或敏感环境变量。
7. 所有重要操作应能关联到现有审计/Trace 体系。
8. 取消、暂停、恢复、重试等控件必须遵循后端真实支持的状态转换。

## 10. 响应式、可访问性与交互细节

即使主要使用场景是桌面宽屏，也必须保证常见窗口尺寸可用。

- 宽屏：允许多列统计、表格和详情面板；
- 中等宽度：减少列数，允许侧栏折叠；
- 窄屏：导航转为抽屉/紧凑模式，复杂表格提供横向滚动或卡片视图；
- 不允许关键操作被裁切或只能通过悬停发现；
- 所有交互控件有键盘焦点状态；
- 对话框打开后管理焦点，关闭后恢复焦点；
- 表单字段有可读标签和错误说明；
- 图表应有文本摘要或表格替代信息；
- 颜色对比度和 axe 扫描纳入验收；
- 尊重减少动态效果偏好。

## 11. AI 执行流程与阶段划分

本指南不授权 AI 自动启动整个 UI 改造。用户提出具体任务后，按对应批次执行。

### Phase 0：只读审计（每次新会话/重大任务开始时）

检查：

- 根目录 `AGENTS.md` 与仓库 `AGENTS.md`；
- `README.md`、`docs/SESSION-HANDOFF.md`、`docs/README.md`；
- `web/package.json`、锁文件、目录结构；
- 路由、页面、布局、组件和 Token；
- API Client、TanStack Query 使用方式；
- 当前 REST/MCP/CLI/Workflow 契约；
- 现有测试、截图和视觉基线；
- Figma 当前 Design System 和目标画板；
- Git 工作区状态。

输出或更新本批次审计记录。只读阶段不做大规模修改。

### Phase 1：基础体系对齐（只在审计发现确有缺口时执行）

- 把 Figma 现有色彩、字体、间距和圆角映射到项目现有 Token；
- 统一全局应用壳层；
- 整理重复组件；
- 补齐必要的基础状态组件；
- 确保现有页面没有视觉或功能回归。

不要为了“重新整理”而重写已经稳定的组件。

### Phase 2：按用户指定模块增量完善

一次选择一个模块或一个明确的垂直切片，例如“Knowledge Base 资源列表筛选和详情”。

每个切片至少包含：

1. 业务目标与用户流程；
2. 现有代码和 API 检查；
3. Figma 画板/组件检查；
4. 最小实施计划；
5. UI 与真实数据连接；
6. 加载/空态/错误/权限状态；
7. 单元、集成或 E2E 测试；
8. 视觉截图验收；
9. 文档和变更记录。

### Phase 3：跨模块一致性

在多个模块逐步完善后，检查：

- 导航一致；
- 表格、筛选和详情模式一致；
- 状态标签语义一致；
- 错误和空状态一致；
- 组件没有重复实现；
- API 和业务边界没有被破坏；
- 全局 Token 修改没有造成其他页面回归。

### Phase 4：持续维护

每次新增功能时：

- 更新对应 Figma 画板或记录待同步项；
- 复用现有组件；
- 更新 API/UI 映射；
- 补充测试；
- 更新变更日志；
- 不把尚未实现的能力写成已完成。

## 12. 每批次固定工作流

必须严格执行：

1. **分析需求**：确认用户希望解决的问题和验收范围。
2. **检查源代码**：找到真实页面、组件、API、Schema 和调用链。
3. **检查设计**：核对 Figma、Token 和组件。
4. **最小计划**：列出要改的文件、复用的组件、风险和测试。
5. **实施**：只修改本批次范围。
6. **格式化**：使用项目已配置的格式化工具。
7. **静态检查**：TypeScript、Lint、构建检查。
8. **测试**：Vitest/Testing Library、相关集成测试和 Playwright。
9. **视觉检查**：启动真实 Web 工作台，对目标页面截图；检查桌面与窄视口。
10. **业务回归**：确认 API 契约、状态机、权限、Trace 和后端行为未被破坏。
11. **文档更新**：同步设计、接口映射和变更记录。
12. **汇报**：列明完成项、未完成项、测试结果、风险和后续建议。

不要为了让测试通过而删除测试、降低断言、跳过失败或偷偷改变验收口径。无法运行的检查必须说明原因。

## 13. Figma 与代码同步流程

每次涉及 UI 的任务按以下顺序：

1. 在 Figma 中定位已有画板和组件；
2. 判断本次是已有组件复用、现有画板调整，还是新增页面；
3. 使用现有 Token 和组件进行设计；
4. 对设计变更进行截图检查；
5. 按项目现有组件结构实现；
6. 用浏览器截图对照 Figma；
7. 记录设计与实现差异；
8. 需要时更新 Figma 和文档。

若 Figma 不可访问：

- 继续使用本指南和仓库现有 Token；
- 不得声称 Figma 已同步；
- 将待同步事项记录在变更记录；
- 不得生成伪造的 Figma 页面链接。

## 14. 验收标准

每个页面/功能按适用项验收：

### 视觉

- [ ] 与现有 Figma 基础视觉一致；
- [ ] 颜色、字体、间距、圆角遵循 Token；

- [ ] 操作成功/失败有明确反馈；

### 安全

- [ ] 权限由后端校验；

- [ ] 工具执行不绕过安全执行面；

- [ ] Lint/格式化检查通过；

- [ ] 无无关依赖或大规模重构；
- [ ] 文档与实现一致。

不适用的项目可以标记 N/A，但必须说明理由。

## 15. Git 与工作区安全
