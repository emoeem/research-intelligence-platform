# tun-伪-ack-环境下的协议级端口判活-含-nginx-占位端口识别

> 状态: `script_ok` — 配套脚本 `tun-port-probe.py`
> 本文件说明**为什么这么写**，不是使用手册。用法见脚本头 docstring。

## 为什么需要这个脚本

开着 sing-box / clash 的 TUN 模式时，任何 TCP connect 都会立即返回成功 —— TUN 栈在本地
就把 SYN 应答了，真正的握手失败要等几百毫秒后才以"无数据"的形式暴露。
于是 nmap -sT 会把所有端口报成 open。

## 判据设计

三层，必须全部通过：
  L1 TCP connect 成功（TUN 环境里没有意义，但要知道它说了什么）
  L2 协议层有响应（80 发 GET 等 HTTP/，443 发 ClientHello 等 ServerHello，
     22 等 SSH-，6379 发 PING 等 +PONG ...）
  L3 阴性对照：连一个必然关闭的端口，确认它不是"也成功"
     —— 关闭端口也 connect 成功 = TUN 在骗你，L2 是唯一可信判据

## 常见误报（先排除这些，再下结论）

① 未知端口要先试 HTTP 再试 TLS —— 绝大多数"非常规端口"其实是 http 服务
② nginx 占位端口：default_server 对任意 Host 返回固定欢迎页，端口活着但没业务，
   必须单独标出来，否则会把一堆占位端口当资产
③ 21/25 的 banner 可能延迟发送，超时设太短会漏判
④ 中间设备可能返回 RST 而不是静默丢弃，两者含义不同（RST = 明确拒绝）

## 验证与收口

输出三分类，报告里要分开写：
  真活    协议层有合法响应
  伪连通  TCP 通但协议层无响应（TUN 伪 ACK / 中间设备静默丢包）
  占位页  有 HTTP 响应但内容是 nginx/apache 默认页
占位端口的正确表述："该端口已监听但未绑定业务站点"，不要当资产报。
