## 主题

前端硬编码密钥型加密 API 通道还原：ECB + hex + `xign` 签名（182 体育实例）


## 通道特征

这类站点的请求体不透明：

```
POST /api/xxx
{"data":"a3f8...（hex 长串）","xign":"b7c2e1..."}
```

- `data` 是 AES 加密后的 hex（**不是 base64**，长度是 32 的整数倍）
- `xign` 是对明文或密文的签名（常见是 md5/sha1 of sortedParams + key）

## 还原顺序

1. **确认是 hex 不是 base64**：hex 只含 `0-9a-f`，且长度 % 32 == 0
2. **试 ECB**：ECB 加密的相同明文块产生相同密文块。把密文按 32 字符切块，
   若出现重复块 → 确认 ECB（CBC 不会）
3. **找 key**：在 bundle 里搜 `Utf8.parse`、`CryptoJS.enc.Hex.parse`、
   `mode:ECB`。key 常见是 16 位（AES-128）或 32 位 hex（AES-128 的 hex 形式）
4. **找 xign 算法**：搜 `xign`，看它签名的是 `data` 密文还是明文
5. **验证**：把明文加密回密文，逐字节相同才算确认

## ECB 的利用价值（比 CBC 高）

- **块重放**：把密文里的某一块替换成另一块的密文，解密后对应位置就是另一段明文
  → 可在不知道 key 的情况下篡改结构化数据（如把 `roleId:1` 换成 `roleId:9`）
- **块字典**：如果某个字段的取值空间很小（布尔、状态码、金额小整数），
  可以预先建立"明文块 → 密文块"的映射表，直接读出明文
- **无 IV**：省掉 IV 猜测这一步

## 常见误报

- 密文长度不是 16 的倍数 → 不是 AES，可能是 RSA 或自定义编码
- 每次请求密文都变但明文相同 → 有随机 nonce 拼在明文里（CBC 或 ECB+nonce）
- 解出来是合法 JSON 但字段全是乱码 → key 对了但编码不对（UTF-8 vs GBK）
