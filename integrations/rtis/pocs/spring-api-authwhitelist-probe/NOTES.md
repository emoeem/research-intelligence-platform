# spring-api-authwhitelist-probe

> 状态: `script_ok` — 配套脚本 `poc.sh`
> 本文件说明**为什么这么写**，不是使用手册。用法见脚本头 docstring。

## 为什么需要这个脚本

Spring Security 的 permitAll() 匹配的是**请求路径**，不是"已认证状态"。两类常见误配：
  W1 路径后缀绕过：/api/admin/users 受限，但 /api/admin/users.json 或 ;.js 被归一化后落到 permitAll
  W2 通配过宽：/api/public/** 放行，但 /api/public/../admin 在容器归一化前先匹配

## 判据设计

三态，缺一不可：
  ① 裸路径返回 401/403（证明它确实受限）
  ② 变体返回 200 且不是登录页/错误页
  ③ 变体响应与随机路径不同（排除 SPA 兜底和全局 200）

## 常见误报（先排除这些，再下结论）

① 裸请求就是 200 → 该接口本来公开，测下去无意义
② 变体返回 200 但是登录页 → 前端兜底，不是绕过
③ 12 个变体里最容易中的是 `;.js`（Tomcat 的路径参数截断）和 `/`（尾斜杠）
④ 有些 WAF 会把 `..;/` 直接拦掉，但 `%2f` 能过 —— 两个都要试

## 验证与收口

必须做的人工收口（不做就会误报）：
  1) 变体返回的是不是**同一份数据**？用 jq 取业务字段比对（.data.items[0].id）
     一致 = 真绕过；空数组 = 只绕过鉴权没拿到数据
  2) 关掉 Cookie 再打一次。带 Cookie 200、不带也 200 → 匿名可访问（更严重）
  3) 用另一个低权账号的 Cookie 重复。能读别人数据 → 水平越权叠加
报告口径：写清"哪个变体 + 绕过的是认证还是授权 + 拿到几个字段"，不要只写"存在未授权访问"。
