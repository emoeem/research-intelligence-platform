## 为什么需要这个脚本

站群（同套模板铺几百个域名）的落地页普遍带 ?from= / ?redirect= / ?r= 这类参数，
用途是"从哪来就回哪去"。三个真实陷阱：
  T1 H2 陷阱：HTTP/2 下 :authority 与 Host 可以不一致，网关按 :authority 做校验、
              按 Host 做路由 → 校验和路由不是同一个值
  T2 路径面：/go?url= 这种跳转中继页往往只校验 referer 不校验目标
  T3 hex2bin：参数经一次 hex/base64 解码后才使用，直接传 https://evil.com 被拦，
              传 68747470733a2f2f... 反而通过

## 判据设计

三条同时成立才报：
  ① 响应是 301/302/303/307/308，Location 指向非本站域名
  ② 随机域名做对照，Location 不指向随机域名（否则是"原样回显"而非跳转）
  ③ Location 里出现我们的唯一标记，证明是我们控制的

## 常见误报（先排除这些，再下结论）

① curl 不执行 JS，前端跳转测不出来 —— 必须浏览器二次确认
② `//evil.com/` 是协议相对 URL，浏览器会跳转到 https://evil.com/，
   很多后端只校验 "http://" 前缀，这是最常漏的一种
③ 空 Location 或 Location 指向根路径 = 跳回首页，不是重定向
④ 站群常在 /go/ /jump? /link? /out? 和短链服务 /s/ 上

## 验证与收口

浏览器二次确认（curl 拿到 302 不等于可利用）：
  1) 打开命中 URL，看地址栏最终落在哪
  2) 若被前端 JS 拦下（location.replace 前做了域名白名单），curl 的 302 不成立 → 降级
  3) 用 //evil.com/ 形式再测，确认能否携带 referer 伪装
报告口径：写清"参数名 + 载荷形态 + 是否需要用户点击 + 能否带 referer"。
