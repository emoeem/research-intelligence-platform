# SRC/众测提交规范

## 一、平台清单与选择

| 平台 | 特点 |
|---|---|
| 各厂自建 SRC（阿里/腾讯/字节/美团/京东/快手/百度/网易/B站/小米/华为） | 厂商资产白名单严格、收录范围精确到域名；定级按各厂标准，分值最高 |
| 补天 butian.net | 泛厂商 + 政企 CNVD 联动；活动多，通用漏洞走证书通道 |
| 漏洞盒子 vulbox.com | 泛厂商众测；对复现步骤完整性要求高 |
| CNVD / CNNVD | 通用型漏洞证书通道（政府侧收录）；事件型走厂商协调 |

选平台顺序：厂商在自建 SRC 白名单内 → 优先自建 SRC；不在 → 补天/盒子（看哪家收录该资产）；通用型组件漏洞（0day 性质）→ CNVD。

## 二、通用定级对照（提交前自评，用 CVSS vector 支撑）

| 级别 | 类型示例 |
|---|---|
| 严重 | 核心 RCE、全量用户数据泄露、支付逻辑（0 元购/任意改价）、管理员接管 |
| 高危 | 未授权访问敏感数据、水平越权到他人账户、SQL 注入（可读敏感表）、存储 XSS（打管理员）、appsecret/token 泄露可全接口 |
| 中危 | CSRF 关键操作、反射 XSS、SSRF（内网可达但无敏感回显）、短信轰炸、信息泄露（无直接危害组合） |
| 低危 | 无危害组合的信息泄露、自 XSS、浅层验证码绕过 |

红线（出 scope / 打真实用户 / 大流量 / 改他人数据）见 knowledge-sources 里 src-hunter-skill 的 compliance.md，提交前逐条比对。

## 三、三段式提交模板

```markdown
标题：<组件/功能> <漏洞类型>（<影响点>）——例： XX 网关 /api/doc 接口未授权访问（全量接口契约泄露）

【漏洞信息】资产: https://x.target.com（SRC 白名单内）；类型: 未授权访问；等级自评: 高危（CVSS 3.1: AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:N/A:N）

【危害】说明谁能拿什么数据/能力（1-3 句，不夸大）

【复现步骤】
1. 请求包（完整 curl/原始 HTTP，敏感字段打码）
2. 响应关键回显（截码不截数据：行数/字段名证明，不贴他人 PII）
3. 可选：最小化利用链说明（能证明到哪一步）

【影响面】受影响接口/数据范围估算（口径写清：抽样 N 条证明可遍历，未全量拉取）

【修复建议】鉴权中间件收口 / 最小权限 / 参数绑定等具体建议
```

## 四、CNVD 流程要点

- **通用型**（产品级漏洞，非特定站点）：原创证明 = 提供公开可复现的测试环境或详尽步骤；重复判定极严（先 CNVD 全库检索组件名+版本）
- **事件型**（特定站点）：走 CNVD-CNC 简化通道，会转交厂商；要附授权证明或说明测试依据
- 证书周期约 1-2 月；同一漏洞勿同时投补天+CNVD（撞车风险，先看平台规则）

## 五、查重自查（提交前 5 分钟）

1. 平台站内搜：目标域名/组件名/漏洞类型（历史收录大概率重复）
2. 自家记录搜：knowledge.db `poc_fts MATCH '目标域名/组件'` + engagement vuln 表（自己重复提交最常见）
3. GitHub 搜：组件 CVE/公开 exp 存在 → 厂商已知的概率高，改角度或换组件版本

## 六、话术纪律（compliance.md 收口）

- 只陈述可证明的事实；评级给 CVSS vector 支撑，不裸写"严重"
- 证据脱敏：他人数据打码/截断；请求包里自己的 token 打码
- 一洞一报，不打包多个洞稀释定级；被拒/争议时先复测再申诉，不情绪化回复
- 提交后留档：原始包+截图 ≥ 平台 disclosure 窗口；回填 knowledge.db（category 按漏洞类型）标注 submitted 状态
