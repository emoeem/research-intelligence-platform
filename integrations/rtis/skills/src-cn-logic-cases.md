# 国内 SRC 实战案例模式库

三个从真实赏金案例（累计 $6000+）提炼的可复用模式。每个模式给出：适用信号 → 判定步骤 → 最小化验证 → 修复建议（写报告用）。

---

## 模式一：403 端点的路径解析不一致（Forbidden → P1）

**适用信号**：目录枚举发现 `/console`、`/admin`、`/actuator`、`/.htaccess`、`/config.php` 等返回 403。403 ≠ 不存在——只说明前端拦了，后端路由很可能还在。

**核心思路**：反向代理/WAF 与后端应用对同一 URL 的**解析结果不一致**。测的是"谁能解析出真实路径"。

**判定步骤（按命中率高到低）**：

```bash
U=https://TARGET/console
# ① 编码变体（代理解码后变成 //path 或 ./path，后端正常路由）
for p in "/%2e$P" "/%252e$P" "/%ef%bc%8f$P" ; do curl -s -o /dev/null -w "%{http_code} $p\n" "$U$p"; done
# ② 路径规范化差分
for p in "/console/" "/console/." "/./console/.." "/;//console" "/.;/console" "/./console/../console"; do ...
# ③ 大小写 / 后缀变体（Ruby 栈 .json）
/CONSOLE  /console.json
# ④ 方法与头（部分端点只拦 GET）
-X POST / -X PUT；X-Original-URL / X-Rewrite-URL 头
```

**工具**：Burp 插件 [403 Bypasser](https://github.com/portswigger/403-bypasser)、[4-ZERO-3](https://github.com/Dheerajmadhukar/4-ZERO-3)（单工具覆盖全部变体）。

**实战链路（$2100 P1 案例）**：`/console` 403 → `/%2e/console` 绕过 → 物联网交付平台内部控制台（构建信息/OS/用户列表/CLI 组件）→ 定 P1。**拿到绕过后立刻 Burp 加全局规则** `/%2e/` 前缀，后续浏览畅通。

**报告要点**：贴前后对比（403 → 200 + 敏感内容截图）；影响按"暴露了什么管理能力"论证，不按"绕过技巧"论证。

## 模式二：多分支流程的防御不一致（登录/短信/验证码）

**适用信号**：登录、找回密码、换绑手机、领券等流程存在**多个分支**——如"微信一键授权登录" vs "手机号手动登录"、"扫码" vs "账密"。防御（验证码、频控、签名）经常只加在主分支上。

**核心思路**：逐分支对照，找"防御梯度"——主分支有频控 + 图形验证码 + 会话绑定，次分支可能一样都没有。

**判定步骤**：

| 对照项 | 主分支（如一键授权） | 次分支（如手动输手机号） |
| --- | --- | --- |
| 图形验证码 | 有，服务端强校验 | 有前端校验？服务端校验吗？ |
| 短信发送频控 | 手机号 + IP + 设备三维度 | 只按手机号？还是完全没有？ |
| captcha token 与 session 绑定 | 绑定 | token 可跨 session 复用？ |
| 请求可重放 | 否 | 重放响应是否 200？ |

**最小化验证**（证明机制缺陷即可，不要放大）：
1. 抓次分支的"发送短信/校验"请求，**用自己控制的两个手机号**各触发一次，对比请求体差异；
2. 去掉/置空 captcha 参数重放 → 仍 200 即证明"校验未强制"；
3. 同一手机号连续触发 3-5 次观察是否触发频控（**到此为止**，能证明无频控就不要再刷）；
4. 报告里只陈述机制缺陷 + 截图频次响应，不展示批量发送效果。

**修复建议（报告里直接给）**：所有分支共享同一个 Rate Limiter；短信发送必须携带与 session 强绑定的 captcha token；按手机号 + IP + 设备指纹多维度限频。

## 模式三：单一泄露端点的全子域复用（$250 → $4000）

**适用信号**：手工侦察捡到一个泄露敏感信息的端点（如 `/api/config`、`/env.json`、`/swagger-ui/`、`/actuator/env`），且目标允许**通配符子域**（`*.target.com`）。

**核心思路**：一个端点在一个子域上泄露 = 大概率是通用代码，**所有子域上都试一遍**。

**判定步骤**：
1. 子域枚举（subfinder + dnsx 过泛解析）拿到子域全量；
2. 把泄露端点拼到每个子域，按状态码分流：`200` 直接取证 → `301` 加 `www.` 前缀再试 → `403` 套模式一的绕过表；
3. 命中的逐个取证、去重、记录（哪些子域、泄露什么、影响面）。

**报告要点**：影响面按"N 个子域 × 内容敏感度"展开，一个通用泄露点被你放大成全资产面问题，定级和赏金都上一个档次。

## 与其它技能的衔接

- 403 绕过拿到入口后 → `hunt-springboot`（actuator 面继续深挖）/ `hunt-source-leak`（源码与密钥）
- 分支频控缺陷 → `hunt-captcha-bypass`、`hunt-forgot-password`（找回链路同款思路）
- swagger/openapi 泄露 → `hunt-shadow-api`、`hunt-api-misconfig`（按契约逐接口测未授权与越权）

> 模式一、三改编自 [Awesome-SRC-experience](https://github.com/owl234/Awesome-SRC-experience)（MIT）403-bypass 与 swagger-leak 案例；模式二改编自其小程序短信逻辑案例。验证环节强调最小化：证明机制缺陷即止，不做放大性测试。
